# Практическая работа 3 — Обработка исключений и валидация данных в Java

## Система банковских переводов

Решены все пять практических частей из задания. Приложение переводит деньги со счёта ACC001 (Aida, 50000) на счёт ACC002 (Dana, 10000), обрабатывает ошибки и после каждой попытки показывает оба баланса. Требования к качеству кода из части 6 также выполнены.

Проект рассчитан на Java 11 и новее, не требует Maven, Gradle или сторонних библиотек. Каждый запуск — одна попытка перевода и новые счета с исходными балансами.

## Часть 1 — Банковский счёт

В `BankAccount` данные закрыты модификатором `private`. Получить номер, владельца и баланс можно через геттеры. Произвольно изменить баланс извне нельзя: операции проходят через `deposit` и `withdraw`, где выполняются проверки.

Конструктор отвергает `null`, пустые строки и строки из пробелов в номере или имени. `null` проверяется первым: вызов `isBlank()` у `null` сам вызвал бы `NullPointerException`. Благодаря короткому замыканию оператора `||` правая часть не вычисляется, если левая уже равна `true`.

```java
if (accountNumber == null || accountNumber.isBlank()) {
    throw new IllegalArgumentException("Номер счёта не может быть пустым.");
}
```

Метод `strip()` удаляет пробельные символы по краям. Например, `" ACC001 "` сохраняется как `"ACC001"`. Номер и владелец объявлены `final`: после создания счёта их нельзя переназначить. Баланс меняется, поэтому у него `final` нет. Нулевой начальный баланс разрешён, отрицательный — запрещён.

`deposit` принимает только положительную конечную сумму. Новый баланс вычисляется в локальной переменной и проверяется до присваивания полю. Поэтому ошибочное пополнение сохраняет прежний баланс.

## Часть 2 — Собственное исключение и списание

`InsufficientFundsException` наследуется от `Exception` и является checked-исключением. Конструктор передаёт сообщение родительскому классу через `super(message)`, после чего обработчик может получить его методом `getMessage()`. Поле `serialVersionUID` задаёт версию сериализуемого класса исключения; к логике перевода оно отношения не имеет.

В `withdraw` сначала проверяется сумма, затем остаток:

```java
public void withdraw(double amount) throws InsufficientFundsException {
    validatePositiveAmount(amount);
    if (amount > balance) {
        throw new InsufficientFundsException(
                "На счёте " + accountNumber + " недостаточно средств.");
    }
    balance -= amount;
}
```

Если сумма недопустима, возникает `IllegalArgumentException`. Если сумма допустима, но превышает остаток, возникает `InsufficientFundsException`. В обоих случаях выполнение прекращается до `balance -= amount`, и деньги остаются на счёте. Снять ровно весь остаток разрешено: используется `>`, а не `>=`.

## Часть 3 — Банковский перевод

`TransferService.transfer` последовательно проверяет:

1. Оба счёта существуют, то есть не равны `null`.
2. Счета различаются как объекты и имеют разные номера.
3. Сумма конечна и больше нуля.
4. Зачисление не приведёт к переполнению баланса получателя.
5. У отправителя достаточно средств — это проверяет `withdraw`.

Только после этих проверок деньги списываются и зачисляются. Затем выводится сообщение об успехе.

**Почему важен порядок операций.** Если сначала списать деньги, а затем обнаружить ошибку пополнения, перевод окажется выполнен частично. В этой программе все условия, при которых `deposit` может отказать, проверяются заранее. Сам `withdraw` также проверяет условия до изменения баланса. Поэтому при предусмотренных ошибках балансы остаются прежними.

Класс `BankAccount` объявлен `final`, чтобы наследник не мог переопределить `deposit` и неожиданно нарушить эти правила. Гарантия относится к этому однопоточному консольному приложению. Для одновременных переводов из нескольких потоков или сохранения в базе данных понадобятся дополнительные механизмы синхронизации или транзакций.

**Почему проверяются и `==`, и `equals`.** Выражение `from == to` обнаруживает один и тот же объект. Метод `equals` у строк сравнивает содержимое номеров. Два разных объекта с одним номером также считаются одним банковским счётом; перевод между ними запрещён. У объектов `BankAccount` собственный `equals` в этой работе не переопределяется.

## Часть 4 — Ввод и обработка ошибок

`Scanner.nextLine()` читает строку целиком, а `Double.parseDouble(...)` преобразует её в число. Такой выбор нужен, чтобы неверный формат давал именно требуемое `NumberFormatException`. При использовании `Scanner.nextDouble()` ошибка формата обрабатывалась бы иначе — через `InputMismatchException`.

В `Main` предусмотрены отдельные обработчики:

- `NumberFormatException` — текст вместо числа, пустая строка или неверный числовой формат.
- `IllegalArgumentException` — недопустимая сумма либо данные.
- `InsufficientFundsException` — суммы на счёте недостаточно.

`NumberFormatException` является подклассом `IllegalArgumentException`, поэтому его `catch` стоит первым. Более общий обработчик не должен предшествовать более частному.

Например, при вводе `100000` строка успешно превращается в число. `Main` вызывает `transfer`, тот вызывает `withdraw`, а `withdraw` выбрасывает `InsufficientFundsException`. Выполнение возвращается к подходящему `catch` в Main. До `deposit` программа не доходит, поэтому оба баланса сохраняются.

После ошибки программа показывает понятное сообщение без аварийного завершения. Блок `finally` всегда выводит при обычном завершении попытки:

```text
Операция перевода завершена
```

Это означает, что попытка закончилась, а не что перевод обязательно успешен. После `try-catch-finally` выводятся оба баланса.

Использован `try-with-resources`: `try (Scanner scanner = ...)`. Он автоматически закрывает Scanner, в том числе при исключении. Здесь программа делает одну попытку и завершается, поэтому закрыть связанный `System.in` допустимо. Для меню с повторным вводом Scanner обычно создают один раз на весь цикл и закрывают после выхода из него.

## Сложные случаи с double

`double` используется в соответствии с заданием. У него есть специальные значения: `NaN` («не число»), `Infinity` и `-Infinity`. Строки `NaN` и `Infinity` успешно разбираются методом `Double.parseDouble`, поэтому одного `catch (NumberFormatException ...)` недостаточно.

Особенно опасен `NaN`: сравнение `NaN <= 0` возвращает `false`. Проверка только на неположительность могла бы пропустить такое значение. Используется условие:

```java
if (!Double.isFinite(amount) || amount <= 0) {
    throw new IllegalArgumentException("Сумма должна быть конечной и положительной.");
}
```

`Double.isFinite` возвращает `false` для всех трёх специальных значений. Проверяется и результат сложения: два конечных больших числа могут дать бесконечность из-за переполнения.

У `double` также есть погрешность двоичного представления дробей: например, `0.1 + 0.2` не представляется точно как `0.3`. Формат `%.2f` округляет только отображение, а не внутренний баланс. Для настоящей финансовой системы обычно выбирают `BigDecimal` с явными правилами округления или целое число минимальных денежных единиц. Здесь сохранён требуемый заданием тип; обязательные тесты используют небольшие целые суммы, представимые точно.

`Locale.ROOT` в `printf` делает вывод с точкой предсказуемым независимо от системного языка. Ввод через `Double.parseDouble` также ожидает десятичную точку: `5000.50`, а не `5000,50`.

## Ответы на контрольные вопросы

### 1. Чем отличаются checked и unchecked исключения? Приведите примеры из своей программы.

**Checked-исключения** проверяются компилятором: если вызываемый метод объявляет такое исключение, вызывающий код должен обработать его через `try-catch` либо объявить передачу дальше через `throws`.

В программе это `InsufficientFundsException`, потому что класс наследуется от `Exception`, но не от `RuntimeException`:

```java
public class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String message) {
        super(message);
    }
}
```

Поэтому вызов `withdraw(amount)` или `transfer(from, to, amount)` требует обработки этого исключения либо соответствующего `throws` у вызывающего метода.

**Unchecked-исключения** не требуют обязательного `catch` или `throws`. К ним относятся `RuntimeException` и его подклассы, а также `Error` и его подклассы. В этой программе используются два подкласса `RuntimeException`:

- `IllegalArgumentException`: недопустимый аргумент, например отрицательная сумма, пустой владелец или отсутствующий счёт.
- `NumberFormatException`: строку нельзя преобразовать в число, например `"abc"`.

Название checked не означает, что ошибка происходит при компиляции. Само исключение возникает во время выполнения; компилятор проверяет только наличие обработки или объявления.

### 2. Для чего используются throw и throws? В чём разница?

`throw` непосредственно выбрасывает **конкретный объект исключения** внутри метода:

```java
if (amount > balance) {
    throw new InsufficientFundsException("Недостаточно средств на счёте.");
}
```

После `throw` обычное выполнение этого метода прекращается: Java ищет подходящий `catch` в текущем методе или выше по цепочке вызовов.

`throws` в объявлении метода сообщает, **какие исключения могут выйти из него**:

```java
public void withdraw(double amount) throws InsufficientFundsException {
    // Проверка суммы и списание денег.
}
```

`throws` сам по себе ничего не выбрасывает и не обрабатывает. Он предупреждает вызывающий код о необходимости обработать checked-исключение или передать его дальше. В объявлении можно перечислить несколько типов через запятую.

В этой программе `withdraw` выбрасывает исключение через `throw`, а `withdraw` и `transfer` объявляют его через `throws`. Метод `Main.main` обрабатывает его через `catch`.

### 3. Чем отличаются catch и finally? Выполнится ли finally, если исключения не произошло?

`catch` обрабатывает исключение подходящего типа. Если исключения не было, блоки `catch` пропускаются. При возникновении исключения выполняется первый подходящий `catch`.

`finally` предназначен для завершающих действий: он выполняется при обычном выходе из `try` и при выходе из-за исключения. **Да, если ошибки не произошло, `finally` тоже выполнится.** Он выполняется и при `return` из `try` или `catch`.

```java
try {
    transferService.transfer(account1, account2, amount);
} catch (InsufficientFundsException e) {
    System.out.println("Перевод отклонён: " + e.getMessage());
} finally {
    System.out.println("Операция перевода завершена");
}
```

Сообщение в `finally` означает завершение попытки операции, а не подтверждение успешного перевода. Об успехе сообщает сам `TransferService`.

Гарантия не распространяется на остановку процесса, аварийное завершение JVM или вызов `System.exit(...)`. Если выполнение вообще не покидает `try`, например из-за бесконечного цикла, до `finally` оно также не дойдёт. В обычных сценариях этой практической работы `finally` выполняется всегда.

### 4. Почему для недостаточного баланса создан InsufficientFundsException, а не IllegalArgumentException?

Положительная и корректно записанная сумма перевода может превышать текущий остаток. Например, сумма `100000` сама по себе допустима, но на счёте отправителя только `50000`.

`IllegalArgumentException` обозначает нарушение требований к аргументу: сумма равна нулю, отрицательна, является `NaN` или бесконечностью. Недостаточный остаток зависит от **состояния счёта**, поэтому для него полезен отдельный тип `InsufficientFundsException`.

Это позволяет раздельно обработать ситуации и дать пользователю точное сообщение. Наследование от `Exception` делает исключение checked: вызывающий код обязан явно предусмотреть такой исход. Для данной работы это требование задания и выбранный контракт метода; в других приложениях разработчики могут выбирать другую модель обработки бизнес-ошибок.

### 5. Что произойдёт, если пользователь введёт abc вместо суммы? Как должна реагировать программа?

`Scanner` прочитает строку `"abc"`. Вызов

```java
double amount = Double.parseDouble(scanner.nextLine().strip());
```

выбросит `NumberFormatException`, потому что строка не представляет число. До вызова `transfer` выполнение не дойдёт, поэтому деньги не спишутся и не зачислятся.

Программа должна перехватить ошибку и показать понятное сообщение, затем вывести сообщение из `finally` и балансы: **ACC001 — 50000.00, ACC002 — 10000.00**.

```java
catch (NumberFormatException e) {
    System.out.println("Ошибка ввода числа: введите число, например 5000 или 5000.50.");
} catch (IllegalArgumentException e) {
    System.out.println("Некорректные данные: " + e.getMessage());
}
```

`NumberFormatException` наследуется от `IllegalArgumentException`. Поэтому специальный `catch (NumberFormatException ...)` ставят **раньше** общего `catch (IllegalArgumentException ...)`. При обратном порядке общий обработчик уже перехватывает все такие ошибки, и компилятор отвергнет недостижимый специальный обработчик.

Так как число преобразуется через `Double.parseDouble`, дробную часть нужно вводить через точку. Например, `1250.50` корректно, а `1250,50` без дополнительной обработки вызовет ошибку формата. Строки `NaN` и `Infinity` этот метод распознаёт, поэтому их нужно отдельно отвергать проверкой `Double.isFinite(amount)`.
